2. Product and design north star
FileSense helps people convert, compress, resize, and prepare files for real upload requirements directly from the file
manager. The primary experience is contextual and task-oriented: right-click → choose a meaningful action → review the
output → create a copy.
Design principles
  Native before branded: use OS-standard title bars, controls, menus, focus rings, keyboard shortcuts, file pickers,
 accessibility APIs, and theme behavior. FileSense branding should not fight the host OS.
 One task per dialog: compression and form preparation should be focused workflows, not mini dashboards full of unrelated
 tiles.
 Progressive disclosure: show the few controls needed for the selected task. Place advanced controls behind a clearly
 labelled disclosure.
 Outcome clarity: explain target size, estimated output, actual result, and any trade-off in plain language.
  Safe by default: original files are never modified, deleted, or overwritten. This must be enforced by the processing layer, not
 only by UI copy.
 Quiet visual hierarchy: use typography, spacing, alignment, and native selection states before adding decoration,
 gradients, badges, or cards.
 Accessible by construction: keyboard-only operation, screen-reader labels, scalable text, visible focus, reduced-motion
 respect, and sufficient contrast.
 Platform truth: each platform may have different entry points and layout. Consistency means consistent behavior, not
 identical-looking windows.
What to avoid
  A web-app layout transplanted into a desktop window: oversized cards, fake browser-like panels, unnecessary persistent
 sidebars, or a dashboard that users must open for every small task.
 Custom-drawn imitations of native controls when a native control is available.
  A context menu with every feature and setting exposed at once.
  Decorative charts, icons, gradients, or status pills that do not help a user make a decision.
  Controls with unclear effects, redundant settings, or values that are not explained.

Architecture implication
Use a shared processing engine and shared task/validation model, but separate platform integration adapters. Avoid
building one fake “universal native UI” that ignores each OS. A cross-platform framework may host the app, but critical
controls and integration points should use platform-native components where practical.

  Declare exact supported OS versions and distributions. Do not say “supports Linux” without listing tested environments.
  If a file-manager integration is unavailable, provide an obvious fallback: Open With, drag-and-drop, or the main app.
  Never block the file manager while compression is running.
  Installers must provide a clear enable/disable option for context-menu integration and uninstall cleanly.

4. Core workflow specifications
A. Make Form-Ready — primary differentiator
  Entry point: the first FileSense item in the context menu, labelled “Make Form-Ready…”.
  Step 1: show selected files and current properties only where relevant (format, dimensions, size, pages).
  Step 2: choose a named preset or Custom. Presets must state their constraints; they do not guarantee compliance with
 every website.
 Step 3: show format, maximum file size, dimensions/crop policy, and PDF readability preference. Keep advanced settings
 collapsed by default.
 Step 4: show the exact output filename and destination before execution.
  Step 5: show actual output size/dimensions, whether the target was met, and actions to open the result or containing folder.

9. Handoff prompt for Claude
You are the product designer and senior cross-platform desktop engineer for FileSense. Use this PDF as the
authoritative design and product brief. The previous design direction was too web-like. Redesign it as a
genuinely native-feeling desktop utility. Do not simply copy the concept image. Use platform conventions and
real controls: - Windows: Fluent/WinUI conventions and Explorer integration. - macOS: native macOS controls,
Finder Quick Actions, standard dialogs, system typography and keyboard behavior. - Linux: explicitly supported
environments first (GNOME/Nautilus and KDE/Dolphin), with native dialogs/theme behavior and documented
fallback. For every screen and component, document: 1. The user need it serves. 2. Why the component is present.
3. Default state, advanced state, validation, errors, loading, success, and cancellation. 4. Keyboard and
accessibility behavior. 5. Platform-specific differences. 6. Tests required before calling it complete. Hard
requirements: - Never modify, delete, or overwrite source files. - Always create a separate output file. -
Default output folder is beside the original; allow a custom destination. - Resolve filename collisions with _2,
_3, etc. - Preview the exact output filename. Do not claim a target size was achieved unless actual output meets
it. - Target size, percentage reduction, and quality level are distinct modes. - If a target cannot be met above

Keep context menus short and task-focused. - Do not claim universal Linux file-manager support. Deliverables, in
order: A. Identify ambiguities and risky assumptions. B. Technical spike plan and dependency/license review. C.
Platform-specific interaction maps. D. A component inventory with rationale; remove anything decorative or

current environment. F. Acceptance tests, accessibility checklist, file-safety tests, and visual QA plan. G. MVP
backlog with measurable exit criteria. Do not implement the full roadmap before the technical spike passes. A
